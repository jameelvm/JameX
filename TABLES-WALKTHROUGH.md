# Catalog tables — a walkthrough with real data

Companion to `README.md` §8 — the long-form version, in plain language, with the
full event payloads and every column accounted for. `README.md` §8.5 carries the
condensed walkthrough; this file is the one to read when a column's purpose is
unclear.

> **Status: all of this is now built and verified** (phase 3, modules 3–6).
> Steps still labelled *(Module 4)* / *(Module 6)* below refer to when the code
> was written, not to anything outstanding. The one exception is **Step 1** —
> Ingest does not exist yet, so nothing publishes `VideoUploaded` in the real
> system until phase 4. Phase 3's handlers were tested by publishing these exact
> events by hand.

## The cast

Three real rows that already exist in `jamex_users`:

| Who | Id | What |
|---|---|---|
| Jameel | `019ffe64-18c3…3093c7` | the account, in `users` |
| @jamex | `019ffe64-4d99…65b9e3` | his channel, in `channels` |

And the video we are about to follow:

| Video | Id |
|---|---|
| "How to Cook Pasta" | `019fff10-0000…000001` |

I shorten the ids here for reading. They are full UUIDs in the database.

---

## Step 1 — Jameel picks a file

He opens the site, chooses `pasta.mp4` (300 MB), types a title, and hits upload.

**Nothing is written to Catalog yet.** The Ingest service handles this part. It
invents the video id straight away — before a single byte has arrived — and
hands it back to the browser so the upload page can show progress.

This is why `videos.id` is *not* generated by the database. The id already
exists, and the file in S3 is already named after it:

```
s3://jamex-raw/uploads/019fff100000700080000000000001/source.mp4
```

If Catalog invented its own id later, nothing could connect the row to the file.

---

## Step 2 — The upload finishes, Ingest announces it

The last chunk lands in S3. Ingest publishes one message to SNS:

```json
{
  "eventId":   "aaaa1111-0000-7000-8000-000000000001",
  "eventType": "VideoUploaded",
  "occurredAt":"2026-08-17T09:00:00Z",
  "source":    "Ingest",
  "data": {
    "videoId":        "019fff10-0000-7000-8000-000000000001",
    "channelId":      "019ffe64-4d99-7104-b959-fa391c65b9e3",
    "uploaderId":     "019ffe64-18c3-7f71-97ff-9ab0653093c7",
    "title":          "How to Cook Pasta",
    "description":    "A simple 10 minute recipe.",
    "categoryId":     "food",
    "tags":           ["cooking", "pasta", "recipe"],
    "defaultLanguage":"en",
    "privacy":        2,
    "rawBucket":      "jamex-raw",
    "rawObjectKey":   "uploads/019fff100000700080000000000001/source.mp4",
    "sizeBytes":      314572800,
    "contentType":    "video/mp4",
    "uploadedAt":     "2026-08-17T09:00:00Z"
  }
}
```

Read the two halves separately:

- **The envelope** (`eventId`, `eventType`, `occurredAt`, `source`) — postal
  information. Every event has it.
- **The data** — the actual news.

Two services are subscribed to `VideoUploaded`: **Catalog** and **Encoder**.
They both get their own copy in their own queue.

## Step 3 — Catalog writes the first row **(Module 4)**

Catalog's handler wakes up and does **two inserts in one transaction**.

### `videos` — one new row

| Column | Value | Where it came from |
|---|---|---|
| `id` | `019fff10…000001` | the event — copied as-is |
| `channel_id` | `019ffe64-4d99…` | the event |
| `uploader_id` | `019ffe64-18c3…` | the event |
| `title` | `How to Cook Pasta` | the event |
| `description` | `A simple 10 minute recipe.` | the event |
| `category_id` | `food` | the event |
| `tags` | `{cooking,pasta,recipe}` | the event |
| `default_language` | `en` | the event |
| `privacy` | `2` | the event (2 = Public) |
| **`status`** | **`1`** | **Catalog decided this** — 1 = Queued |
| `raw_bucket` | `jamex-raw` | the event |
| `raw_object_key` | `uploads/019fff10…/source.mp4` | the event |
| `size_bytes` | `314572800` | the event |
| `content_type` | `video/mp4` | the event |
| `media_bucket` | **NULL** | not encoded yet |
| `master_playlist_key` | **NULL** | not encoded yet |
| `duration_seconds` | **NULL** | nobody has measured it yet |
| `poster_thumbnail_key` | **NULL** | no thumbnails yet |
| `encoder_provider` | **NULL** | no encoder has touched it |
| `encoding_seconds` | **NULL** | — |
| `failure_reason` | **NULL** | nothing has failed |
| `failure_stage` | **NULL** | — |
| `attempt_count` | `0` | — |
| `popularity_tier` | `0` | 0 = Cold. Nobody has watched it |
| `created_at` | `2026-08-17 09:00:01Z` | now |
| `updated_at` | `2026-08-17 09:00:01Z` | now |
| **`published_at`** | **NULL** | **it is public, but not playable yet** |

**The important bit:** eleven columns are NULL. That is not missing data — it is
*honest* data. The video genuinely has no duration and no playlist, because
nothing has looked at the file yet. Those columns get filled in Step 5.

**`published_at` is NULL even though `privacy = 2`.** "Public" is Jameel's
*intention*. "Published" means a viewer can actually press play. Right now they
cannot, so the video must not appear in any feed.

### `processed_events` — one new row

| Column | Value |
|---|---|
| `event_id` | `aaaa1111-0000-7000-8000-000000000001` |
| `event_type` | `VideoUploaded` |
| `source` | `Ingest` |
| `processed_at` | `2026-08-17 09:00:01Z` |

This row means one thing: **"I have already dealt with this message."**

Both inserts happen in the same transaction, so either both are saved or
neither is. There is no state where the video exists but Catalog has forgotten
it handled the event.

---

## Step 4 — The same message arrives again **(Module 4)**

This *will* happen. SQS promises to deliver a message **at least once**, not
exactly once. Common causes:

- the handler took longer than the visibility timeout, so SQS assumed it died
  and gave the message to a second worker
- the handler finished the work but crashed before telling SQS to delete it

So a second copy of that exact message shows up — **same `eventId`**.

The handler tries to insert into `processed_events` again:

```
ERROR: duplicate key value violates unique constraint "pk_processed_events"
```

It sees the collision, concludes "I have done this already", deletes the message
and does nothing else. **No duplicate video row.**

That is the entire inbox pattern. One four-column table and a primary key.

---

## Step 5 — Encoder finishes, Catalog fills in the blanks **(Module 4)**

Meanwhile Encoder has been chewing on the file: making 360p, 720p and 1080p
versions, cutting them into segments, and grabbing thumbnails. It uploads all of
that to `jamex-media` and announces:

```json
{
  "eventId":   "bbbb2222-0000-7000-8000-000000000002",
  "eventType": "VideoEncoded",
  "occurredAt":"2026-08-17T09:04:30Z",
  "source":    "Encoder",
  "data": {
    "videoId":            "019fff10-0000-7000-8000-000000000001",
    "mediaBucket":        "jamex-media",
    "masterPlaylistKey":  "videos/019fff10…/master.m3u8",
    "durationSeconds":    612.5,
    "renditions": [
      { "label":"360p",  "width":640,  "height":360,  "bitrateKbps":800,
        "codec":"h264", "playlistKey":"videos/019fff10…/360p/playlist.m3u8",
        "sizeBytes":61000000,  "segmentCount":103 },
      { "label":"720p",  "width":1280, "height":720,  "bitrateKbps":2500,
        "codec":"h264", "playlistKey":"videos/019fff10…/720p/playlist.m3u8",
        "sizeBytes":191000000, "segmentCount":103 },
      { "label":"1080p", "width":1920, "height":1080, "bitrateKbps":4500,
        "codec":"h264", "playlistKey":"videos/019fff10…/1080p/playlist.m3u8",
        "sizeBytes":344000000, "segmentCount":103 }
    ],
    "posterThumbnailKey": "videos/019fff10…/thumbs/t2.jpg",
    "encoderProvider":    "FFmpeg",
    "encodingSeconds":    268.4,
    "encodedAt":          "2026-08-17T09:04:30Z"
  }
}
```

Catalog's handler now does **five writes in one transaction**.

### `videos` — the same row, updated

Only these columns change:

| Column | Before | After |
|---|---|---|
| `status` | `1` (Queued) | **`3` (Ready)** |
| `media_bucket` | NULL | `jamex-media` |
| `master_playlist_key` | NULL | `videos/019fff10…/master.m3u8` |
| `duration_seconds` | NULL | `612.5` |
| `poster_thumbnail_key` | NULL | `videos/019fff10…/thumbs/t2.jpg` |
| `encoder_provider` | NULL | `FFmpeg` |
| `encoding_seconds` | NULL | `268.4` |
| `updated_at` | 09:00:01 | `09:04:31` |
| **`published_at`** | NULL | **`2026-08-17 09:04:31Z`** |

`published_at` gets set **now**, not at upload time, because only now can a
viewer actually press play. The moment it is set, the video appears in the
public feed — because `ix_videos_published` only indexes rows where
`privacy = 2 AND status = 3`, and this row now qualifies.

Notice the id, title, tags and raw file columns were **not touched**. The row
was never rewritten, only extended.

### `renditions` — three new rows

| id | video_id | label | width | height | bitrate_kbps | codec | playlist_key | size_bytes | segment_count |
|---|---|---|---|---|---|---|---|---|---|
| `…c1` | `019fff10…` | 360p | 640 | 360 | 800 | h264 | `…/360p/playlist.m3u8` | 61000000 | 103 |
| `…c2` | `019fff10…` | 720p | 1280 | 720 | 2500 | h264 | `…/720p/playlist.m3u8` | 191000000 | 103 |
| `…c3` | `019fff10…` | 1080p | 1920 | 1080 | 4500 | h264 | `…/1080p/playlist.m3u8` | 344000000 | 103 |

One row per quality option. This is what lets the player switch quality when
the network slows down — it is the same video, three different sizes.

`video_id` has a **real foreign key** to `videos`, because both tables live in
this same database. Compare with `videos.channel_id`, which has no foreign key,
because channels live in `jamex_users` — a different database this service is
not allowed to touch.

### `processed_events` — one new row

| `event_id` | `event_type` | `source` |
|---|---|---|
| `bbbb2222-…-000002` | `VideoEncoded` | `Encoder` |

A **different** `eventId` from Step 3, so no collision. This is a genuinely new
message and it gets applied.

### Why the unique index on `(video_id, label)` matters

If this `VideoEncoded` message is redelivered, the inbox check catches it first.
But suppose a bug let the handler run twice anyway — it would try to insert a
second `720p` row for the same video, and the database would refuse:

```
ERROR: duplicate key value violates unique constraint "ix_renditions_video_id_label"
```

Two independent safety nets. The player can never be offered "720p" twice.

## Step 6 — What the watch page reads

Someone opens the video. Catalog answers with one row plus its renditions:

```
SELECT * FROM videos WHERE id = '019fff10…';
SELECT * FROM renditions WHERE video_id = '019fff10…' ORDER BY bitrate_kbps;
```

Catalog does **not** know the channel is called "JameX Official" — that lives in
Identity. It only knows `channel_id`. The Gateway asks Identity for the name and
stitches the two together. That is the price of separate databases, and the
reason `/channels/batch` exists.

## Step 7 — The unhappy path **(Module 4)**

Suppose the file was corrupt. Encoder retries, gives up, and publishes:

```json
{
  "eventId":   "cccc3333-0000-7000-8000-000000000003",
  "eventType": "VideoEncodingFailed",
  "source":    "Encoder",
  "data": {
    "videoId":      "019fff10-0000-7000-8000-000000000001",
    "reason":       "No audio track found in source file",
    "stage":        "probe",
    "attemptCount": 3,
    "failedAt":     "2026-08-17T09:03:10Z"
  }
}
```

`videos` is updated:

| Column | Value |
|---|---|
| `status` | `4` (Failed) |
| `failure_reason` | `No audio track found in source file` |
| `failure_stage` | `probe` |
| `attempt_count` | `3` |
| `published_at` | stays **NULL** |

Now Jameel sees a real error message instead of a spinner that never stops. And
because `published_at` stayed NULL, the broken video never reaches a feed.

This is what those three "failure" columns are for. Without them the only honest
answer to "what happened to my video?" is "no idea".

## Step 8 — Jameel deletes the video **(Module 6)**

He clicks delete. Catalog does **two writes in one transaction**:

**1. Delete the video row.** The three `renditions` rows disappear
automatically — that is `ON DELETE CASCADE`. No cleanup code needed.

**2. Insert one `outbox_messages` row:**

| Column | Value |
|---|---|
| `id` | `019fff20-…-000009` |
| `event_type` | `VideoDeleted` |
| `payload` | `{"eventId":"dddd4444…","eventType":"VideoDeleted","data":{"videoId":"019fff10…","channelId":"019ffe64-4d99…","deletedAt":"…"}}` |
| `occurred_at` | `2026-08-17 11:00:00Z` |
| `published_at` | **NULL** ← not sent yet |
| `attempt_count` | `0` |
| `last_error` | NULL |

### Why not just call SNS directly?

Because that is two separate systems with no shared transaction:

```
1. DELETE the video      → saved to Postgres ✅
2. …server crashes here…
3. publish VideoDeleted  → never happens     ❌
```

The video is gone from Catalog, but **Search still lists it forever** and
Engagement still holds its counters. Nobody notices, and nothing can detect it.

The outbox fixes this by making step 2 part of step 1. The event is saved to the
same database, in the same transaction. If the delete survived, so did the
intention to announce it.

### Then a background relay sends it

Every second or so, a background job runs:

```sql
SELECT * FROM outbox_messages WHERE published_at IS NULL ORDER BY id LIMIT 50;
```

It publishes each one to SNS, then stamps the row:

| Column | After |
|---|---|
| `published_at` | `2026-08-17 11:00:01Z` |

Now the row is invisible to that query forever. This is why
`ix_outbox_messages_unpublished` is a **partial index** — it only contains rows
where `published_at IS NULL`. Ten million sent messages, and the index still
holds only the handful still waiting.

If SNS is down, `attempt_count` climbs and `last_error` records why, so a stuck
message is *visible* instead of silently retried forever.

### And if it gets sent twice?

It might. The relay could publish successfully, then crash before stamping
`published_at`, and send the same event again on restart.

That is fine — Search and Engagement each have their own `processed_events`
table and will ignore the second copy.

**This is the whole trade:** the outbox turns *"the event might vanish forever"*
into *"the event might arrive twice"*. The first is unfixable data corruption.
The second is solved by four columns and a primary key.

---

## The four tables in one sentence each

| Table | Its one job |
|---|---|
| `videos` | What the video **is** — assembled from three different events over five minutes |
| `renditions` | The quality options a player can switch between |
| `processed_events` | "I already handled that message" — stops duplicates being applied twice |
| `outbox_messages` | "I promised to tell everyone" — stops announcements being lost |

## The one rule behind the design

**A video row is never written all at once.** Three different services each know
part of the truth:

- **Ingest** knows where the file is
- **Encoder** knows how long it is and what qualities exist
- **Catalog** owns the row and decides what the status means

None of them can see the others' databases. So they send each other events, and
Catalog assembles the row over time. Every NULL column in Step 3 is a fact
nobody knew yet — and every one of them gets filled by Step 5.
